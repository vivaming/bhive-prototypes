# Offline editorial protocol and scheduler harness

`review-protocol.mjs` is a deterministic contract for review packet integrity. It binds article, chart, data, rubric, policy, and identity-registry versions into one hash; requires a separately versioned and verified writer/model-family registry record; and requires distinct fact-check, rebuttal, data-risk, legal-ethics-risk, and editorial roles. Every reviewer has a verified identity/model-family record. Fact-check and rebuttal families must be distinct from the writer and one another; this fixture contract currently enforces unique family IDs across all assigned identities. Claim evidence must identify exact source hash, snapshot, and row locator. An unresolved critical contradiction or high-risk flag forces `HOLD` regardless of votes. A changed locked version invalidates earlier approval. Its most permissive result is `READY_FOR_HUMAN_RELEASE_REVIEW`; `releaseAuthorized` and `modelCalled` are always false.

This module is a protocol/test harness. Registry records are fixture inputs, not a connected or trusted reviewer directory. It does not run an LLM, determine factual truth, approve publication, or authorize release. The review-service API, real reviewer identity controls, signed attestations, and CMS integration remain unavailable in this repository.

`daily-scheduler.mjs` simulates a daily target using only candidates explicitly marked `APPROVED` and `topicEligible`, and lanes explicitly marked `freeEligible` with `paid: false`. It reserves lane and quota-group capacity, derives stable idempotency keys, reuses same-version work only when every stored reservation still maps to an enabled free lane at its current version, rejects stale or duplicate events, retries 429/failure outcomes only within remaining free quotas, and reports shortfall when eligible capacity is exhausted. Paid, disabled, unknown, or outdated prior lane reservations cannot be reused as completed work. It has no network client, dispatch, credential, paid fallback, or publishing path. Existing lane metadata and quotas in tests are illustrative contracts, not verified XPI capability claims.

Run `pnpm workflow:qa` for the focused adversarial suite, `pnpm release:qa` for release-manifest checks, or `pnpm qa:all` for the complete local suite. A passing dry run means only that the supplied fixture satisfies the local rules. Live model registry evidence, XPI lane availability/quota enforcement, the article review server, and CMS remain blockers for production workflow execution. Release safety rules live in `release/README.md`; no deployment or publication path is enabled.
